# 09 - Signed Receipts [ES](README.md)

## Purpose

This example shows how to generate and verify signed receipts for sensitive
actions executed by an MCP server.

A signed receipt is portable evidence that allows a specific claim to be
verified as having been signed by a particular key and that its data was not
modified afterward.

This example uses a simulated action. It does not modify Kubernetes, Docker,
Terraform, local files, or any external system.

> These signed receipts can be applied alongside the tools mentioned above,
> adding an extra layer of validation and security.

## What problem does it solve?

Internal logs are useful for debugging and auditing operations within an
organization. However, some workflows may need to transport evidence to
another system or team.

For example:

- An agent requests a sensitive operation.
- An MCP server validates the request.
- The operation requires authorization and human confirmation.
- The server records the result.
- A signed receipt is generated.
- Another system verifies the receipt later.

The receipt makes it possible to verify that its contents were not altered
after signing.

## What a signature does not prove

A valid signature does not, by itself, prove:

- That the operation was correct.
- That the identity was authorized.
- That the human confirmation was authentic.
- That the server was not compromised.
- That the execution environment was trustworthy.
- That the business result was correct.
- That the operation complied with every policy.

The signature mainly proves:

- Which data was signed.
- That the data was not modified.
- Which key produced the signature.

For that reason, a signed receipt does not replace validation, authorization,
human confirmation, logs, or provider audits.

## Example flow

```text
sensitive action requested
          |
          v
input validation
          |
          v
authorization check
          |
          v
human confirmation
          |
          v
simulated action
          |
          v
input and output recorded
          |
          v
data hashed
          |
          v
signed receipt
          |
          v
later verification
```

## Key management modes

This example allows the private key used to sign receipts to be selected
through a signing provider.

### Ephemeral

Generates a new key in memory every time the server starts:

```bash
MCP_SIGNING_MODE=ephemeral
```

This is useful for quick tests, but receipts can no longer be verified after
the server restarts because the previous key disappears.

### Local

Loads or creates a persistent key in a local file:

```bash
MCP_SIGNING_MODE=local
MCP_SIGNING_KEY_PATH=keys/dev-signing-key.pem
```

This is the recommended mode for MCP Inspector because receipts remain
verifiable after the server restarts.

The local key must remain outside version control and use restrictive
permissions, such as `600`.

### Production example

Represents integration with an external key provider:

```bash
MCP_SIGNING_MODE=production
```

In a real environment, the key should come from a KMS, HSM, or secret manager.
This example uses an environment variable only as a teaching adapter:

```bash
MCP_SIGNING_PRIVATE_KEY_B64=<external-key-required>
```

Never include real private keys in the repository, the Inspector configuration,
or the receipts.

## MCP Inspector profiles

The `mcp-inspector.json` file includes three profiles:

| Profile | Key management | Use |
| --- | --- | --- |
| `signed-receipts-ephemeral` | In-memory | Quick tests |
| `signed-receipts-local` | Local file | Development and Inspector |
| `signed-receipts-production-example` | External provider | Conceptual example |

Each entry starts an independent process. A receipt generated by one profile
must not be verified with another profile because they may use different keys.

For the complete flow, always use the same profile:

1. Run `simulate_sensitive_action`.
2. Copy the generated receipt.
3. Run `verify_signed_receipt`.
4. Paste the receipt contents.

## Key identification

Each receipt includes a `key_id`, derived from the public key used to sign it:

```json
{
    "key_id": "a9e01b77fd639ee1"
}
```

The `key_id` is not a private key and cannot be used to sign receipts. It
identifies the key that produced the signature and supports future key
rotation.

### Important Inspector note

In MCP Inspector, the input field for the tool already represents the
`receipt` argument. Paste only the inner receipt object; do not wrap it in
another `receipt` property. Otherwise, the object becomes nested twice and
verification fails even when the original signature is correct.

## Included tools

#### `simulate_sensitive_action`

Simulates a sensitive action such as:

```text
restart_service
deploy_service
```

The tool receives:

| Field | Description |
| --- | --- |
| `action` | Simulated action |
| `target` | Target service or resource |
| `actor` | Declared identity |
| `environment` | `development`, `staging`, or `production` |
| `authorized` | Indicates whether the request is authorized |
| `human_confirmed` | Indicates whether human confirmation exists |

Example:

```json
{
    "action": "restart_service",
    "target": "api",
    "environment": "staging",
    "authorized": true,
    "human_confirmed": true
}
```

The response includes a simulated operation and a signed receipt:

```json
{
    "ok": true,
    "simulated": true,
    "output": {
        "status": "simulated",
        "message": "No external resource was modified."
    },
    "receipt": {
        "action": "restart_service",
        "actor": "user-123",
        "environment": "staging",
        "target": "api",
        "input_hash": "...",
        "output_hash": "...",
        "key_id": "...",
        "signature": "..."
    }
}
```

#### `verify_signed_receipt`

Receives a receipt and checks whether its signature is still valid:

```json
{
    "receipt": {
        "action": "restart_service",
        "actor": "user-123",
        "environment": "staging",
        "target": "api",
        "input_hash": "...",
        "output_hash": "...",
        "key_id": "...",
        "signature": "..."
    }
}
```

Valid response:

```json
{
    "valid": true,
    "message": "The receipt signature is valid."
}
```

If any signed data is changed, verification fails:

```json
{
    "valid": false,
    "message": "The receipt signature is invalid."
}
```

## Rejected examples

### Unauthorized actor

```json
{
    "action": "deploy_service",
    "target": "api",
    "actor": "user-123",
    "environment": "production",
    "authorized": false,
    "human_confirmed": true
}
```

Response:

```json
{
    "ok": false,
    "error": "not_authorized",
    "message": "The actor is not authorized for this action."
}
```

### Missing human confirmation

```json
{
    "action": "restart_service",
    "target": "api",
    "actor": "user-123",
    "environment": "staging",
    "authorized": true,
    "human_confirmed": false
}
```

Response:

```json
{
    "ok": false,
    "error": "confirmation_required",
    "message": "Human confirmation is required."
}
```

## How the receipt is built

Before signing, the server calculates hashes for:

* The received input.
* The produced output.
* The relevant operation data.

It then groups this data into a deterministic structure and signs it with an
Ed25519 key.

The signature covers the complete receipt contents except for the `signature`
field itself.

```text
input
   |
   v
input_hash
   |
   v
output
   |
   v
output_hash
   |
   v
action + identity + environment + hashes + key_id
   |
   v
digital signature
```

## Receipt tampering

After creating the receipt, suppose this value is changed:

```json
{
    "target": "api"
}
```

to:

```json
{
    "target": "database"
}
```

The signature no longer matches the contents and verification returns:

```json
{
    "valid": false
}
```

This demonstrates the integrity of the receipt, not the absolute truth of the
original operation.

## Signing key

All three modes use Ed25519 keys, but each provider obtains the private key in
a different way:

* `ephemeral` generates a new private key in memory.
* `local` loads or creates a persistent private key in a local file.
* `production` obtains the key through an external provider.

In a real environment:

* The private key must not be stored in the repository.
* It must be stored in a secure system.
* A key rotation process must exist.
* Access must be restricted.
* The public key must be distributed through a trusted process.
* A revocation procedure must exist.
* The authority allowed to sign must be clearly defined.

Only receipts signed with `ephemeral` lose their verification capability after
a process restart. The `local` provider preserves its key across restarts.

## Best practices

### Do not sign every event

Signed receipts should be reserved for relevant actions, such as:

* Deployments.
* Terraform changes.
* Kubernetes changes.
* Service restarts.
* Configuration changes.
* Database writes.
* Actions between teams or providers.
* Operations that are difficult to reverse.

For ordinary queries, normal logs and audits may be sufficient.

## Do not include secrets

The receipt must not include:

* Passwords.
* Tokens.
* Private keys.
* Complete environment variables.
* Cloud credentials.
* Unnecessary personal data.

Only the data necessary to support the claim should be signed.

## Separate authorization from evidence

The field:

```json
{
    "authorized": true
}
```

only simulates the flow in this example. In a real system, the server should
not blindly trust this value when it is supplied by the client.

Authorization should come from:

* An authenticated identity.
* A policy system.
* An identity provider.
* A verifiable session.
* An independent authorization service.

## Capture evidence from the executing system

A signature generated by the client only proves what the client claims to have
observed.

To demonstrate what the server actually executed, the receipt should be
generated by a trusted authority on the server side or by the executing
system.

## What the tests demonstrate

The tests verify:

* An authorized action produces a receipt.
* An unauthorized action is rejected.
* Missing human confirmation is rejected.
* A valid receipt can be verified.
* A tampered receipt is no longer valid.

## Example limitations

This example does not:

* Execute real actions.
* Modify infrastructure.
* Manage real permissions.
* Authenticate users.
* Implement key rotation.
* Protect a production key.
* Prove the truth of the result.
* Replace external logs or audits.
* Provide regulatory compliance.

The purpose is to demonstrate how a simulated operation can produce signed
evidence and how later modifications to its data can be detected.

## Summary

A signed receipt should be understood as:

```text
portable evidence
+
cryptographic integrity
+
signer identity
```

It should not be understood as:

```text
automatic authorization
+
absolute truth
+
security guarantee
```

In a real DevOps server, a signed receipt should be added after validation,
authorization, human confirmation, execution, and internal recording of the
operation.

> The signature proves that the receipt was not altered and that a specific
> key signed it; it does not, by itself, prove that the operation was correct
> or authorized.
